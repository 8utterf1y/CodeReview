# 代码-设计文档一致性审查工具面试说明

## 一、介绍话术

我在实习期间开发了一个代码-设计文档一致性审查工具，主要用于在研发流程中辅助判断 MR 代码变更是否完整、准确地实现了需求文档中的功能约束。工具会调取内部需求文档和 MR 变更信息，基于 Git Diff 定位变更范围，并结合 AST/Tree-sitter 构建符号索引和双向调用链，形成需求、变更和代码之间可追溯的证据上下文。

在审查层面，我没有直接让大模型对整仓代码做自由判断，而是将需求声明、变更片段、源码符号和调用关系映射为稳定证据对象，再通过确定性状态机约束审查流程，引导大模型依次完成语义初判、反向质疑、定向取证和结论收敛。最终输出与需求条目对应的一致性结论，重点指出未完成、实现偏差或证据不足的部分，并保留代码证据引用，便于研发人员复核。

## 二、详细流程说明

### 1. 输入与审查范围确定

工具的输入主要包括业务仓库路径、需求文档路径、MR 信息、base/head 版本、代码路径过滤条件以及需求章节过滤条件。

审查开始时，运行时会先确定审查边界，例如本次是针对一个 MR、一个提交范围、某几个代码目录，还是某几个需求章节。这里的目标是避免无边界地扫描全仓，也避免模型在没有明确上下文的情况下做泛化判断。

如果提供 MR 信息，工具会锁定 base/head commit，用于保证审查对象稳定。后续如果要把结果回流到 MR，也可以基于锁定的 head commit 做一致性校验，避免代码已经变化但审查结果仍被发布。

### 2. 需求文档解析

需求文档按普通 Markdown 文档处理。工具会基于标题、段落、列表等结构拆分出候选需求声明，并为每条声明生成稳定的 Claim ID。

这一步的重点不是做复杂自然语言生成，而是把大段需求文档转成可逐条审查的结构化对象。比如一个功能需求、一个权限约束、一个状态流转规则、一个异常处理要求，都可以被拆成独立的审查单元。

对于文档版本、负责人、修订记录这类元信息，工具会在审查中标记为 not_applicable，因为它们不是可执行代码行为，不应该被当成代码缺陷。

### 3. Git Diff 变更定位

工具会基于 base/head 生成 Git Diff，提取本次变更涉及的文件、行号和代码片段。Diff 的作用是确定审查的起点：模型和索引系统优先关注 MR 修改过的逻辑，而不是从整仓随机搜索。

在实际审查中，Diff 证据可以回答三个问题：

- 这次 MR 改了哪些文件和函数；
- 某个需求相关逻辑是否在本次变更范围内；
- 如果发现问题，能否归因到本次 MR 引入、暴露，还是无法归因。

没有 base 版本时，工具仍然可以做快照式审查，但只能判断目标代码当前是否符合需求，不能可靠判断问题是不是由本次变更引入。

### 4. AST/Tree-sitter 符号索引

代码层面，工具会对源码构建结构化索引。对于 Python 等语言，可以提取模块、类、函数、方法、常量、变量以及引用关系；对于其他语言，可以通过 Tree-sitter 查询扩展语法解析能力。

索引的核心价值是把代码从纯文本变成可定位、可引用的结构化证据。例如某个需求要求“大额费用必须经过财务审批”，工具不只搜索“大额”这个关键词，而是会定位阈值常量、审批方法、状态枚举、状态流转函数以及相关调用点。

当前实现支持文件哈希复用：如果文件内容没有变化，会复用前一次快照中的符号和调用边，避免每次都重新解析所有文件。但在大仓场景下，仍需要进一步优化为基于 Git blob SHA 的基线索引和 MR 增量覆盖，这样常规 MR 的成本主要和变更文件及受影响调用边相关，而不是和整个仓库规模线性相关。

### 5. 双向调用链构建

仅看 Diff 文件通常不够，因为很多需求是否满足取决于上下游调用关系。例如：

- 修改了 service 方法，需要查看 controller 是否正确调用；
- 修改了状态流转函数，需要查看后台任务是否绕过原子接口；
- 修改了校验逻辑，需要查看创建、审批、取消等入口是否都经过同一校验；
- 修改了公共函数，需要查看调用方是否受到影响。

因此工具会以 Diff 命中的符号或需求相关符号为种子，沿 callers 和 callees 两个方向做有界扩展。也就是既看“这个函数调用了谁”，也看“谁调用了这个函数”。

这里需要设置节点上限和扩展深度，避免在大仓中无限展开。常见策略是先扩展 1 到 2 跳，如果大模型在反向质疑或取证阶段发现证据缺口，再按 gap 定向补充上下文。

### 6. 证据对象与上下文包

工具不会把所有代码直接塞给大模型，而是将需求声明、Diff 片段、源码符号、调用边、代码片段和元数据统一转成稳定证据对象。每个证据对象都有 evidence_id，报告中的判断必须引用这些证据。

这种设计有两个好处：

- 可追溯：最终结论能回到具体需求、文件、函数和代码片段；
- 可约束：模型只能基于已提供证据判断，证据不足时必须输出 uncertain，不能凭经验猜测。

对于长文档或大代码库，工具会分页提供上下文。模型每次只处理有限数量的需求声明，并在需要时通过上下文工具继续取证。

### 7. 多阶段审查引擎

审查流程由确定性状态机编排，核心阶段包括 L3 快速筛查和 L4 深度复核。

L3 阶段负责对每条需求声明做初步判断，输出 consistent、inconsistent、uncertain 或 not_applicable。这个阶段强调覆盖率，要求所有需求声明都有明确状态，不能遗漏。

当 L3 出现 inconsistent 或 uncertain 时，工具会进入 L4 深度复核。L4 分为四个子阶段：

- 初判：大模型基于当前证据提出候选问题和初步原因；
- 质疑：主动寻找误报可能，例如是否存在其他调用路径、是否有替代实现、是否需求本身不可执行；
- 取证：围绕证据缺口继续扩展代码上下文和调用链；
- 收敛：合并重复问题，剔除误报，确定严重级别、归因和最终结论。

这里大模型承担的是证据约束下的语义推理工作，例如理解需求语义、识别实现偏差、比较代码行为和文档约束。确定性运行时负责 Git、索引、状态流转、证据校验、覆盖率门禁和报告生成，避免审查过程完全依赖模型自由发挥。

### 8. 结果输出

最终报告面向研发人员阅读，不应该堆砌所有中间过程，而应该围绕需求条目给出结论：

- 哪些需求已完成；
- 哪些需求没有实现或实现有偏差；
- 哪些需求因为证据不足无法定案；
- 每个问题对应的需求原文、代码位置和证据引用；
- 如果没有 base 版本，需要说明无法做变更级归因。

更适合实际使用的报告应该简洁，重点展示“不符合需求的点”和“需要人工确认的点”。中间的状态机阶段、完整 JSON、覆盖率细节可以保留在机器可读结果中，但不应作为用户阅读报告的主体。

### 9. 大仓库下的性能设计

如果仓库很大，而 MR 只修改少量文件，每次全量解析全仓会浪费时间。更合理的设计是“基线索引 + MR 增量覆盖 + 按需调用链扩展”。

基线索引可以在主干分支或稳定版本上预先构建，按 Git blob SHA 缓存文件级解析结果。MR 审查时，只解析新增或修改文件，删除、重命名和未变更文件通过索引映射处理。然后以 Diff 命中的函数、类、常量为种子，在既有调用图上做有限扩展。

这样常规 MR 的审查成本主要由三部分组成：变更文件解析、受影响符号定位、调用链局部扩展。只有在首次接入仓库、索引版本升级、解析器变更或缓存失效时，才需要重新构建大范围索引。

需要注意的是，不能只看 Diff 文件。因为很多一致性问题出现在变更文件与未变更调用方之间，例如取消逻辑、支付逻辑、权限入口和状态机约束。因此最佳方案不是“只审 Diff”，而是“以 Diff 为入口，按需扩展到受影响上下文”。

## 三、面试答辩可能问答

### Q1：这个工具解决的核心问题是什么？

它解决的是需求文档和代码实现之间缺少自动化一致性校验的问题。传统代码审查更关注代码风格、缺陷和安全问题，但很难系统判断代码是否完整实现了需求约束。这个工具把需求声明、MR 变更、源码符号和调用链组织成证据上下文，再引导大模型做语义审查，输出可追溯的一致性结论。

### Q2：为什么不能直接把需求文档和代码交给大模型判断？

直接交给大模型会有三个问题：上下文容易超长，判断过程不可控，结论难以追溯。我的设计是先用确定性程序完成文档拆解、Diff 定位、AST 索引和证据构建，再让大模型在受控证据范围内做语义推理。这样可以降低幻觉，并且每个结论都能回到具体证据。

### Q3：大模型在里面具体做了什么？

大模型主要做语义层面的判断，包括理解需求声明、判断代码行为是否满足需求、识别实现偏差、提出反证方向、根据补充证据收敛结论。它不负责随意扫描文件、不负责修改业务代码，也不负责决定流程跳转。流程编排、证据校验和覆盖率控制由确定性运行时完成。

### Q4：为什么要做 AST/Tree-sitter 索引，而不是关键词搜索？

关键词搜索只能找到文本相似的位置，但无法稳定理解代码结构。AST/Tree-sitter 可以提取类、函数、方法、常量、引用和调用关系，从而把代码变成结构化证据。例如需求里写“审批金额超过阈值需进入财务审批”，代码里可能对应的是一个 Decimal 常量、一个状态枚举和一个 transition 调用，关键词不一定完全匹配，但结构化索引可以把这些证据关联起来。

### Q5：双向调用链有什么必要？

只看被修改函数内部容易漏掉上下游影响。向 callees 扩展可以看到当前逻辑依赖了哪些底层方法，向 callers 扩展可以看到哪些入口会触发这段逻辑。很多一致性问题本质上是“某个入口绕过了统一接口”或者“某个调用方没有遵守状态约束”，这类问题必须通过双向调用链才能发现。

### Q6：为什么要设计多阶段审查，而不是一次性输出结论？

一次性输出容易把证据不足、误报和真实缺陷混在一起。多阶段审查把过程拆成候选识别、反向质疑、定向取证和结论收敛。先提出问题，再主动找反证和缺口，最后再定案。这个流程更接近人工资深 reviewer 的审查方式，也更适合减少误报。

### Q7：确定性状态机的作用是什么？

状态机用于约束审查流程，保证每个阶段只能按顺序推进，提交结果必须符合结构要求，并且所有需求声明必须被覆盖。它解决的是 Agent 容易跳步、漏审、重复判断和输出格式不稳定的问题。模型负责推理，状态机负责流程和质量门禁。

### Q8：如果仓库很大，每次审查会不会很慢？

不应该每次全量重建索引。合理做法是维护主干基线索引，MR 审查时只解析变更文件，并把增量结果覆盖到基线索引上，再从 Diff 命中的符号出发做局部调用链扩展。当前实现已经支持未变化文件的哈希复用，但更理想的工程化方向是基于 Git blob SHA 做内容寻址缓存，进一步减少大仓下的重复读取、重复解析和重复建边。

### Q9：只审查 Diff 文件可以吗？

不够。Diff 是入口，但不是完整上下文。需求是否满足经常取决于未修改代码中的调用方、状态流转、权限入口、配置和公共方法。如果只看 Diff，容易漏掉“变更代码被谁调用”以及“是否绕过统一逻辑”。所以应该以 Diff 为种子，按影响范围扩展，而不是只看 Diff。

### Q10：如何控制误报？

主要通过四个机制控制：第一，证据不足必须标记 uncertain；第二，L4 阶段强制做反向质疑，主动寻找误报原因；第三，提交结果时校验证据 ID、Claim ID 和覆盖率；第四，报告只把有需求依据和代码证据的问题作为定案缺陷输出。

### Q11：如何保证结果可追溯？

每条需求声明都有 Claim ID，每段代码证据都有 Evidence ID，审查结论必须引用对应证据。报告里可以看到需求原文、相关代码位置、调用关系和判定理由。这样研发人员不用相信模型本身，而是可以沿着证据链复核结论。

### Q12：这个工具和普通代码审查 Agent 有什么区别？

普通代码审查 Agent 通常关注代码质量、安全漏洞、性能和风格问题；这个工具关注的是代码是否满足需求文档。它的核心不是泛化找 bug，而是建立需求到代码的证据映射，并围绕需求条目逐项判断完成度。

### Q13：为什么不默认自动修复代码？

需求一致性问题往往涉及业务语义，自动修改风险较高。工具可以生成建议 Patch 或修复方向，但默认不直接改业务代码。更合理的方式是先输出证据充分的问题报告，由研发人员确认后，再在独立分支上生成修复建议。

### Q14：为什么可以说它是工程化落地，而不是简单 prompt？

因为它不只是写了一段审查提示词，而是包含输入边界控制、需求结构化、Git Diff 定位、AST/Tree-sitter 索引、调用图扩展、证据对象管理、状态机编排、覆盖率门禁和结果生成。Prompt 只承担语义推理的一部分，核心稳定性来自确定性工程链路。

### Q15：如果面试官问你最大的技术难点是什么？

可以回答：最大的难点是如何在有限上下文中让大模型做可靠审查。我的处理方式是把问题拆成两层：底层用确定性工具构建可追溯证据，包括需求声明、Diff、符号和调用链；上层让大模型基于证据做语义判断，并通过状态机强制执行反证分析和补充取证。这样既利用了大模型的理解能力，又避免它在大仓代码中自由猜测。

### Q16：后续还可以怎么优化？

可以从三个方向优化：第一，把索引升级为基线索引加 MR 增量覆盖，降低大仓审查成本；第二，增强跨语言 Tree-sitter 支持和跨服务调用关系建模；第三，把输出报告进一步产品化，只展示需求对应的缺陷、证据和修复建议，中间过程作为审计日志保留。
