# 代码-设计文档一致性审查工具答辩问答

## 阅读与答辩策略

这份文档按真实答辩中的关注顺序组织：先回答主管、业务负责人和项目评审最关心的“为什么做、实际价值、最大难点、如何落地”，再回答技术面试官可能追问的索引、证据、状态机和工程实现。

答辩时建议把项目称为“代码-设计文档一致性审查工具”或“一致性审查 Agent”，不要把“子 Agent”或“插件”当作项目的主体。前者是专用执行角色，后者只是当前的交付和接入形式。

## 0. 项目一句话

这是一个面向 MR 场景的代码-设计文档一致性审查工具。它会调取需求文档和代码变更，基于 Git Diff、AST/Tree-sitter 符号索引和双向调用链构建证据上下文，再通过确定性状态机约束大模型完成语义初判、反向质疑、定向取证和结论收敛，最终输出可追溯的一致性问题报告。

代码实现上，OpenCode 插件位于 `spec-review-opencode/src/index.ts`，负责注册 `/spec-review` 命令、`spec-review` 专用 Agent 和 `spec_review_*` 工具；Python 运行时位于 `spec-review-opencode/runtime/spec_review_runtime/`，负责 Git 范围解析、需求解析、索引、取证、状态机、覆盖率校验和报告生成。

说明：当前代码里部分接口沿用了 `pr`、`GitHub` 命名；在公司内部场景下，面试表述可以统一替换为“内部 MR 平台”“MR 链接”“base/head 版本”。

## 1. 主管与业务负责人高频问题

### BQ1：请不讲技术，先说这个工具解决了什么问题？

它解决的是“代码已经提交，但很难快速确认是否完整、准确地实现了需求”这个问题。现有 MR 审查往往更关注代码写得对不对，而不是需求有没有被完整实现。这个工具将需求条目与本次变更及其上下游代码逐项对照，帮助审查人更快找到遗漏、偏差和证据不足的地方。

### BQ2：为什么现有的人工 MR 审查不够？

人工审查不是做不到，而是很难稳定地做到“需求逐条覆盖”。审查人需要在长文档、Diff、原有实现和调用关系之间反复切换，容易更关注明显改动，忽略权限、幂等、异常分支、状态流转等细节。工具的价值不是取代 reviewer，而是先做一轮系统化对照，让人把时间用在高风险判断上。

### BQ3：这是真实需求，还是为了使用大模型而找的场景？

这个场景在没有大模型时就存在：需求文档和代码属于两种表达体系，传统工具能检查语法、规则和类型，却很难理解“大额费用需财务复核”与某组常量、状态和方法之间的对应。大模型提供了跨文档和代码的语义理解能力，但项目重点是如何把这种能力变成可控、可复核的工程流程，而不是简单接入模型。

### BQ4：这个工具最适合哪些项目？

最适合需求文档相对规范、业务规则较多、MR 审查成本较高的项目，例如涉及权限、审批、计费、状态流转、幂等和审计的系统。对于只修改文案、样式或者没有可验证需求的小改动，投入收益会比较低，应允许快速跳过或只做轻量筛查。

### BQ5：它不适合解决什么问题？

它不是通用质量门禁，不能替代编译、单元测试、安全扫描、性能压测和真实运行环境验证。它也不适合在需求本身含糊、过时或互相矛盾时直接给出“代码错误”结论；这类情况应暴露需求歧义或证据缺口，由人确认。

### BQ6：这个工具和普通代码扫描工具有什么本质区别？

普通扫描工具基于预先定义的规则查找已知模式，例如某个 API 不能调用或某类参数必须校验。本工具的输入是每次可变的自然语言需求，它要理解需求语义，再寻找代码中可能分散在多个文件和调用层级中的实现证据。因此，一个是“固定规则命中”，另一个是“动态需求与代码行为的语义对齐”。

### BQ7：它和普通 Code Review Agent 有什么区别？

普通 Code Review Agent 通常从 Diff 出发，尽可能发现各类代码问题。本工具以需求声明为审查单元，要求每条可验证需求都有结论，且结论必须能回溯到变更片段或源码证据。它追求的不是“尽量多找 bug”，而是“需求是否被覆盖、为什么这样判断”。

### BQ8：如果只是让大模型读需求和 Diff，不也能做吗？

小仓库和简单 MR 可以，但稳定性不够。一次性提示容易受上下文截断、注意力分散和首次判断偏差影响，而且无法保证所有需求都被检查。当前代码先把需求拆成 Claim，再用 Diff、符号和调用关系构建有界证据包，并通过覆盖率和证据 ID 校验约束模型。差别在于，一个是单次问答，一个是可校验的审查流程。

### BQ9：项目中最难的部分是什么？

最难的不是解析 Diff 或调用模型，而是确定“模型应该看什么，以及什么情况下才能定案”。需求可能落在常量、状态机、底层方法或未修改的调用方中；只看 Diff 会漏，扫全仓又会引入大量无关内容。所以我把 Diff 当作起点，通过符号索引和双向调用链只扩展必要上下文，并将证据不足作为独立结论，而不是强行判错。

### BQ10：你在这个难点上做了什么具体设计？

我将系统拆成“确定性证据层”和“大模型语义判断层”。前者解析需求、锁定 base/head、计算 Diff、建立符号与调用索引，并生成带路径、行号和版本的证据对象；后者只在这些证据范围内完成语义初判、反向质疑、定向补证和结论收敛。运行时再校验 Claim 覆盖和 Evidence 归属，使模型不能跳步骤或凭空定案。

### BQ11：为什么需要四个审查阶段，会不会设计过度？

四阶段不是为了把流程做长，而是针对模型常见的两类错误：首次看不到就判定未实现，以及找到一处相似代码就判定已实现。初判负责形成候选，质疑负责主动找替代实现或前置校验，取证只围绕未解缺口扩展，收敛再合并同根因问题。而且并非所有 MR 都跑深审：`auto` 模式先做快速覆盖，只对不一致或不确定项升级。

### BQ12：你如何证明结果值得信任？

我不把“模型说得像真的”当作可信。每个结论都必须对应真实 Claim，引用当前审查案例中已持久化的 Evidence ID，并通过覆盖率门禁。如果缺少可支撑定案的代码或需求原文，系统必须输出 `uncertain`，不能把“没看到”包装成“没实现”。因此可信的核心是结论可回溯、约束可执行、错误可复核。

### BQ13：如果模型结论错了，谁负责？

当前定位是审查辅助工具，最终判断仍由 MR reviewer 负责。工具默认只读，不自动修改业务代码；在结果回流时也应先预览，再经人工确认发布。这一定位与静态扫描类似：工具提供有证据的风险提示，但不绕过现有质量责任体系。

### BQ14：如何避免这个工具给研发增加额外负担？

接入时不应要求研发重复填写大量参数，而是从 MR 获取 base/head 和变更范围，从仓库或内部文档系统调取关联需求。输出也不应展示大量中间状态和全部通过项，用户主报告只需列出“哪条需求未完成、具体偏差、代码证据和建议”。只有出现问题或不确定项时，才需要研发介入。

### BQ15：这个项目的业务价值如何衡量？

不应只看“调用了多少次”，而应看审查效率和结果质量。试点时可以记录四类指标：平均人工对照时间的变化；已知缺陷集上的召回率与误报率；需求 Claim 覆盖率和 `uncertain` 比例；以及问题在合入前被发现的数量。当前代码已有覆盖和回归验证机制，但如果没有真实线上数据，答辩时不应虚构节省比例。

### BQ16：目前已经做到哪一步？

当前已完成可运行的本地闭环：需求 Claim 解析、base/head 范围解析、Git Diff、AST/Tree-sitter 索引、双向调用链、分页证据包、多阶段状态机、证据引用校验、覆盖率门禁和最终报告。OpenCode 端也已封装命令、专用 Agent 和工具接口。公司化落地还需要将当前的外部代码平台适配层替换为内部 MR 平台，并基于真实仓库完成试点评估。

### BQ17：如果说“已落地”，需要满足什么条件？

“完成工程实现”与“在公司生产流程落地”是两件事。后者至少需要：能通过内部 MR 获取真实 base/head 和 Diff；权限、凭证和数据边界符合公司规范；在代表性仓库上通过精度和性能验收；结果可安全回流 MR；并有清晰的人工复核和问题反馈机制。如果实际只做到本地试点，答辩时应如实说“完成可接入工程闭环”，不夸大为全量上线。

### BQ18：如果需求文档本身写得不好怎么办？

系统先区分可验证需求和文档元数据，对无法映射到代码行为的内容标记 `not_applicable`。对含糊、缺少条件或相互冲突的需求，不应转化为代码缺陷，而应以 `uncertain` 和具体缺口提示需求负责人确认。这也会反向暴露需求文档中不可验证的表述，但它是附加价值，不应与代码一致性结论混淆。

### BQ19：如果一个 MR 只改几行，为什么还要看其他代码？

因为代码的实际行为由调用关系共同决定。一个 MR 可能只修改一个入口，但校验在被调方；也可能修改一个公共方法，却影响多个未修改的调用方。因此 Diff 用来确定起点和变更责任，不能机械地作为证据边界。

### BQ20：大仓库每次运行会不会很慢？

当前实现会复用未变文件的索引事实，但仍需要遍历源文件并计算哈希，所以超大仓库上仍有优化空间。更合理的生产方案是“主干基线索引 + MR 增量覆盖 + 按需调用链扩展”：日常 MR 只解析变更文件，再从变更符号向相关上下游扩展。这样主要成本与变更和影响范围相关，而不是每次重建整仓。

### BQ21：如果公司有很多语言和仓库，如何推广？

不应一开始就承诺覆盖所有语言。可以先选择需求规范、业务风险高、技术栈相对统一的仓库试点，建立已知案例集和可接受的误报基线。索引层以 Tree-sitter 查询和语言适配器扩展，MR 平台以 Provider 适配，而 Claim、证据、状态机和报告层保持通用。

### BQ22：如果误报很多，用户很快就不会再用，你怎么解决？

首先不将工具立即设为强阻断门禁，而是先以建议模式运行，统计哪类需求、语言和调用模式容易误报。其次，主报告只呈现有明确需求与代码证据的问题，证据不足单独标记，不混入缺陷数。最后，利用 reviewer 的确认、驳回和原因标注建立回归集，逐步调整取证范围和定案标准。

### BQ23：你怎么处理漏报？

漏报有两个主要来源：需求没有被纳入审查，或者已审查但证据召回不足。前者用 Claim 拆分和覆盖率门禁控制；后者用 Diff 种子、双向调用链和缺口导向取证来降低。还需要用已知缺陷版本持续回归，将“应该发现但没有发现”的案例转化为索引、召回或审查策略改进项。

### BQ24：你如何用真实案例说明这个工具的价值？

可以使用费用支付回归案例说明。需求要求“已取消单据不能被付款”，问题版本的后台任务绕过了原子 `claim_for_payment`，直接将 `{APPROVED, CANCELLED}` 转为 `PAYING`。如果只看新增代码是否能运行，这段逻辑可能看起来完整；但将需求、状态迁移和原有并发控制调用链联系起来，才能识别出“取消后仍可付款”的业务风险。

### BQ25：这个案例为什么不能靠一条固定规则发现？

因为“不能对已取消单据付款”是业务语义，而不是通用语法错误。固定规则除非事先知道项目中所有状态、合法迁移和付款入口，否则无法通用地表达。本工具由需求提供当次审查的业务约束，再由模型结合状态枚举、迁移方法和调用路径做语义对齐。

### BQ26：这个工具对团队的意义只是节省审查时间吗？

不只是时间。第一，它把“需求是否实现”从口头经验变成可追踪的审查记录；第二，它将一些经常被忽略的边界条件提前到合入前暴露；第三，审查中频繁出现的需求歧义可以反向推动文档规范化；第四，结构化 Claim 和 Evidence 为后续的测试生成、影响分析和发布门禁提供了共用基础。

### BQ27：如果主管说“我们已经有测试了”，你怎么回答？

测试验证的是已经被编写成用例的行为，而一致性审查先检查需求是否在代码中有完整实现证据。如果某个需求分支同时没有实现、也没有对应测试，测试套件仍可能全部通过。两者应该互补：审查工具发现需求缺口，测试再提供运行时验证。

### BQ28：如果主管问“为什么不直接自动修代码”？

因为需求一致性问题往往涉及业务取舍，证据足以指出偏差，不一定足以唯一确定正确修复。自动写代码还可能跨越组件边界、改变兼容性或引入新风险。因此当前默认只读，最多生成建议 Patch，由人工确认后再创建独立修复变更，审查和写入权限必须分开。

### BQ29：如果要在公司内部试点，你会怎么推进？

我会分三步。第一步选一个需求文档规范且历史缺陷可回放的仓库，离线评估召回、误报和耗时；第二步以“不阻断、不自动发评论”的影子模式运行，由资深 reviewer 对结果打标；第三步在指标稳定后接入 MR Review Summary，先作为建议项，再决定是否对少数高置信、高风险规则启用门禁。

### BQ30：这个项目的投入成本主要在哪里？

成本不只是模型 token。还包括内部需求文档和 MR 平台的适配，不同语言索引的维护，主干基线索引的计算与存储，以及用于评估的真实案例集。运行成本则可通过快速筛查、按需深审、增量索引和证据分页控制。是否值得推广，应根据试点中节省的 reviewer 时间和提前发现的高风险偏差来衡量。

### BQ31：为什么当前做成插件，而不是独立平台？

插件只是交付方式，目的是让审查能力进入开发者已有的 Agent 工作流，降低部署和使用门槛。核心审查运行时与宿主界面是分层的，后续既可以替换为公司自研 Agent 框架适配，也可以通过 MCP 暴露工具能力。独立平台需要额外的用户、权限、任务调度和界面系统，在验证核心价值前不是必要投入。

### BQ32：如果换一个大模型，系统还能工作吗？

核心运行时不依赖某个特定模型的自由文本格式，因为它通过结构化 schema 接收阶段结果，并在运行时校验 Claim、Evidence 和覆盖率。更换模型后需要重新评估其语义判断、指令遵循和工具调用稳定性，但 Git、索引、证据、状态机和报告层可以复用。这是将模型作为可替换推理组件，而不是把整个系统绑定在一段 Prompt 上。

### BQ33：如果项目继续做，你认为最优先的三件事是什么？

第一是接入真实的内部 MR 和需求文档数据，否则无法验证真实使用体验。第二是建立由历史缺陷和 reviewer 标注构成的评估集，用召回、误报、不确定率和耗时验收，而不是只看演示效果。第三是完成基线索引与 MR 增量覆盖，使大仓审查的性能和资源成本可控。

### BQ34：如果只能保留一个核心价值，你会保留什么？

我会保留“需求结论与代码证据的可追溯对应”。模型、插件形式、索引后端和报告格式都可以替换，但如果一个“未完成”结论不能回答它对应哪条需求、看了哪些代码、还缺什么证据，那么它对真实审查流程的价值就很有限。

## 2. 不同角色可能如何追问

### 研发主管

- 这个工具能不能降低高级工程师的审查负担？回答时强调它承担需求逐条对照和证据搜集，不替代架构取舍和最终批准。
- 为什么不直接改造现有 Code Review Agent？回答时强调审查对象、覆盖门禁和证据模型不同，但两者可以共用 MR 入口。
- 什么时候值得阻断 MR？只有在特定仓库经过充分评估，且结论高置信、高风险、证据完整时才可考虑；初期应只提示。

### 业务或产品负责人

- 工具如何理解业务术语？回答时说明大模型负责语义对齐，但定案必须回到需求原文和代码证据。
- 需求改了怎么办？每次 case 锁定需求和代码版本，新需求应重新生成 Claim 并做增量审查。
- 这能否反向检查需求文档？可以暴露不可验证、冲突或缺少边界条件的声明，但不应自行替业务人员确定真实意图。

### 平台或工程效能负责人

- 接入一个新仓库需要什么？需求文档来源、MR Provider、语言解析能力、仓库权限和评估用例。
- 如何做多仓隔离？当前 case、索引和报告按仓库存放；平台化后还需要仓库级身份、凭证和存储隔离。
- 如何控制运行成本？使用基线索引、Diff 增量、Top-K 证据、分页上下文、快筛后按需深审。

### 质量或安全负责人

- 模型会不会读到不该读的代码？证据召回必须在已授权仓库和审查范围内，生产落地还需使用公司允许的模型与数据通道。
- 如何避免报告引用过时代码？审查时锁定 base/head，回流前再校验 head 是否变化。
- 能否对审查本身做审计？Claim、Evidence、阶段提交和最终结论均有结构化记录，可以还原结论来源。

## 3. 从 MR 到审查结论的核心原理问答

### PQ1：AST 是什么？

AST 是抽象语法树，它把源代码从字符串转换为有层次的语法结构。例如 Python 中一个类、方法、赋值和函数调用，在 AST 中分别是不同类型的节点。工具不再只知道某个词出现在文件里，而是能知道它是函数定义、常量赋值，还是某个方法内部的调用。

### PQ2：Tree-sitter 是什么？它和 AST 是什么关系？

Tree-sitter 是一个多语言增量语法解析器。严格来说，它生成的是保留更多语法细节的具体语法树，而 AST 通常是进一步抽象后的结构。在本项目中，两者都被用来提取同一类索引事实：符号定义、起止行和调用引用。Tree-sitter 的优势是各语言使用对应 grammar，可以用类似的查询方式提取定义和引用，比为每门语言手写文本解析器更容易扩展。当前代码优先使用 Tree-sitter；如果本地没有对应原生语法模块，Python 会降级使用标准库 `ast`。

### PQ3：为什么不直接用关键词搜索？

关键词只能找到文本相似的位置，不能稳定回答命中位于哪个函数、是定义还是调用、上下游是谁。例如 `cancel` 可能同时出现在注释、状态枚举、方法名和测试中。AST/Tree-sitter 先把它们放回语法结构，再以符号为单位组织证据，可以降低纯文本命中带来的噪声。

### PQ4：当前索引具体提取了什么？

它会为受支持的源文件记录语言、内容哈希、解析后端和解析状态；再提取类、函数、方法、常量或变量等 Symbol，记录名称、限定名、类型、起止行和签名；同时提取函数内部的调用，形成 `caller -> callee` 边。它目前是语法级索引，不等于编译器级类型推导、完整数据流或真实运行轨迹。

### PQ5：这个索引算代码知识图谱吗？

广义上可以说它具有轻量代码图谱的基础，因为节点是文件和符号，边是调用关系。但更准确的表述是“符号索引和调用图”，因为当前并未系统建模继承、类型、数据流、接口实现、数据表和跨服务关系。答辩时不宜把它夸大成完整代码知识图谱。

### PQ6：为什么用户必须提供仓库？只提供 MR Diff 不行吗？

Diff 只包含本次增删改的片段，不包含完整的符号边界和未修改上下游。要判断一个入口是否绕过公共校验，或一个底层方法会影响哪些调用方，必须读取 head 版本的仓库源码并建立索引。本地 Git 仓库还用于解析 base/head、计算三点 Diff 和确定报告对应的代码版本。

### PQ7：提供仓库是不是意味着把全部代码发给大模型？

不是。当前 Python 运行时在本地遍历和解析仓库，模型通过 `spec_review_context` 只获得和当前 Claim 相关的有界证据包，包括少量 Diff、源码片段和调用边。代码中每页默认 3 条 Claim，每条的源码证据、Diff 和图边都有上限。生产落地时还需要保证所使用模型、网络通道和日志策略符合公司代码数据规范。

### PQ8：一个 MR 进来后，整个索引与审查流程是什么？

完整链路可以概括为：

1. 接收需求文档、MR 或手工 base/head，以及可选路径和章节范围。
2. 解析并锁定 base/head Commit；MR 模式在独立 worktree 中分析 head，避免污染开发者工作区。
3. 对 head 版本的受支持源文件建立快照索引，未变文件复用上次 Symbol 和 Edge 事实。
4. 计算 `base...head` Git Diff，拆成带文件、新旧行号和片段文本的 change seed。
5. 根据新代码行号找到包含该行的最小 Symbol，将 Diff hunk 映射到变更函数、方法或常量。
6. 将需求文档拆成带稳定 `CLAIM-*` ID 的可审查声明。
7. 对每条 Claim，用需求词、章节和可选查询词对变更 Symbol 及 Diff 做初步相关性排序。
8. 从排名靠前的变更 Symbol 出发，向 callers、callees 或两个方向做有界图扩展。
9. 读取相关 Symbol 的源码区间，将 Diff 和源码片段持久化为 `EVID-*` 证据对象。
10. 专用 Agent 分页获取逐 Claim 证据包，完成快速审查，对有争议项进入四阶段深审，最后由运行时验证并生成报告。

### PQ9：所谓“根据 MR 建立索引”，是只索引 MR 修改的文件吗？

当前代码不是只索引 MR 文件。`build_or_update_index` 会遍历当前分析仓库中受支持的源文件，读取并计算 SHA-256；若与上一快照一致，就复用原有符号和调用边，只重新解析变化文件。这样可以保留全仓调用关系，但在超大仓上仍有遍历和哈希成本。更完整的生产方案应升级为主干基线索引、Git blob SHA 变更检测和 MR delta overlay。

### PQ10：为什么不只索引 MR 改动文件？

因为调用链的另一端往往没有改动。如果只索引 MR 文件，可以看到新方法内部做了什么，却可能看不到谁会调用它，也看不到它调用的仓储层方法是否真的具有原子状态保护。正确的优化是复用主干全仓基线，MR 只解析变化部分，而不是完全放弃未变代码的索引。

### PQ11：Git Diff 是怎么映射到符号的？

`scope.py` 先解析 unified diff 的 hunk 头，得到文件路径、old/new 起始行、行数和增删改类型。然后以 head 快照的 `new_start` 查询“起止行包含该行的最小 Symbol”，将 hunk 绑定到对应函数或方法，并写入 `change_seeds`。这些种子是后续需求相关性排序和调用图扩展的起点。

### PQ12：这种 Diff 映射有什么已知局限？

当前主要基于 head 快照和 `new_start` 映射符号。对于纯删除的方法，head 中已经没有该 Symbol，可能只保留 Diff 证据而无法建立完整的符号种子。更严谨的方案是同时维护 base 和 head 两个索引快照：新增行映射 head，删除行映射 base，再对 Symbol 做版本间对齐。这是当前实现可以继续加强的地方。

### PQ13：需求和代码是怎么初步建立关联的？

当前证据召回的第一步是可解释的词项相关性排序，而不是先让模型自由搜全仓。系统将 Claim statement、章节和定向查询词分词，对变更 Symbol 的名称、限定名、路径和部分源码计分，同时对 Diff 文本排序。大模型再在召回的证据包中判断需求语义与实际代码行为是否一致。

### PQ14：为什么不直接用向量数据库做需求-代码检索？

向量检索可以提高语义召回，但不能自然回答函数边界、调用方、被调方和精确行号。这个项目首先需要可审计的结构化证据，因此以 Diff、符号和调用图为主。后续可以在首轮种子召回中增加 embedding 或代码搜索引擎，但召回后仍要转换为可引用的源码 Evidence 才能定案。

### PQ15：双向调用链是如何构建的？

解析源码时，工具将函数或方法记录为 Symbol；如果在某函数中发现了调用，就记录一条从当前 Symbol 指向目标名称的 `calls` 边。全部文件解析后，再根据目标的普通名或限定名在快照内解析：唯一命中标记为 probable，多个候选标记 ambiguous，无命中保留 unresolved。取证时，沿出边查 callees，沿入边查 callers，因此可以从同一种子向上、向下或双向扩展。

### PQ16：什么是 callers 和 callees？分别解决什么问题？

`callees` 是当前函数调用的下游方法，用于查看底层校验、状态迁移、仓储事务或外部网关调用。`callers` 是调用当前函数的上游入口，用于检查是否存在另一个入口绕过统一校验。例如付款服务的正常入口可能正确使用原子领取方法，但后台批任务是另一 caller，它可能直接改状态而绕过限制。

### PQ17：双向调用链会不会无限扩展？

不会。`context.py` 使用有界 BFS，从排名靠前的种子 Symbol 出发，用 visited 集合防止环路重复，并受 `maxNodes` 和图边数量限制。普通阶段的节点预算较小，取证阶段可以扩大，但仍有上限。如果边未解析、有歧义或达到预算，系统会将它记录为 gap，而不是假装调用链已完整。

### PQ18：调用链准确吗？能直接用它证明缺陷吗？

不能。当前目标解析主要依据名称，唯一候选也只标记为 probable；对重载、别名、动态分派、反射和依赖注入存在局限。所以调用图的定位是“证据导航”：帮助找到应该读的源码，不能单独作为 consistent 或 inconsistent 的定案证据。当前 Prompt 也明确禁止只根据图边或符号名定案。

### PQ19：如果变更是配置、SQL、声明式路由或跨服务调用，调用图不适用怎么办？

这些是当前索引的能力边界。Diff 文本仍可以作为证据，但只有函数调用边不足以还原行为时，应输出证据缺口或 `uncertain`。后续可扩展不同类型的边，例如路由到 handler、配置键到读取点、ORM 实体到数据表、RPC 客户端到服务接口。如果审查风险较高，还可接入 LSP、编译器、测试或运行时 Trace 作为补充证据。

### PQ20：模型在整个过程中具体做了什么？

模型不负责计算 Git Diff、解析 AST、伪造调用图或自己决定下一阶段。这些由确定性运行时完成。模型的核心任务是阅读 Claim 与候选代码证据，理解自然语言需求与代码行为的语义对应；提出候选偏差；尝试寻找能推翻首判的反证；将未解问题表达为定向取证查询；最后在证据充分时生成结构化结论。

### PQ21：所谓“四阶段审查”是怎么形成的？

四阶段指 L4 深审的 `initial -> challenge -> investigate -> converge`：

1. `initial` 对每个候选说清需求期望、已观察代码、候选差异和未证实前提。
2. `challenge` 不是重复初判，而是主动寻找替代实现、前置防护、不可达路径、配置开关或版本归因等反证。
3. `investigate` 只围绕上一阶段形成的证据缺口，按 claimId、query 和 callers/callees 方向补充取证。
4. `converge` 根据初判、反证和补证去除误报，合并同根因，给出严重级别、变更归因和最终结论。

在四阶段之前还有 L3 快速审查。`auto` 模式先对全部 Claim 做 L3，只将 `inconsistent` 或 `uncertain` 升级到 L4；`deep` 模式则直接从 L4 初判开始。

### PQ22：四个阶段是四个子 Agent 相互辩论吗？

不是。当前代码是“单个专用 Agent + 多阶段状态机”，同一个 `spec-review` Agent 按顺序完成四个阶段，不会再创建其他 Agent。这样可以共享同一 case、Claim、Evidence 和历史阶段结果，也减少多 Agent 间信息丢失和成本。“反向质疑”是一种审查职责切换，不代表必须有独立红队 Agent。

### PQ23：那它到底是子 Agent、插件还是审查工具？

从能力上说，它是代码-设计文档一致性审查工具；从当前 OpenCode 执行形式上说，它是一个专用子 Agent；从部署形式上说，它被封装在 OpenCode 插件目录中。子 Agent 说明“谁执行”，插件说明“怎么安装到宿主”，运行时和工具接口才是核心能力。如果换成公司自研 Agent 框架，可以替换入口适配层，保留 Python 审查运行时。

### PQ24：如果只是在 Prompt 里告诉模型按四阶段做，它不跳步骤吗？

只靠 Prompt 不够，当前有三层约束：

1. 权限层：OpenCode 配置对该 Agent 默认拒绝所有工具，只允许 `spec_review_*`，使它不能用 shell、grep 或 edit 绕过证据流程。
2. 协议层：Prompt 要求保存 repo/case_id，按 `next_action` 执行，分页覆盖所有 Claim，并只能引用上下文包中的 Evidence ID。
3. 运行时层：后端保存当前 stage，只接受当前阶段的一次 JSON 提交；没有提交不能 `next`；上一阶段验证通过后才会进入固定后继状态。

真正让流程可靠的是第三层，Prompt 主要用于说明职责和输出语义。

### PQ25：运行时具体会校验什么？

它会校验提交阶段是否等于当前 stage，结果是否为合法 JSON 对象，是否包含逐条 claims/results，`claim_id` 是否真实且不重复，verdict 是否在四个合法枚举中，`evidence_id` 是否属于当前 case 和当前 Claim，以及当前阶段的所有期望 Claim 是否被恰好覆盖。`consistent` 和 `inconsistent` 如果没有代码证据会被直接拒绝；伪造 Claim、跨 Claim 引用证据或用“其余需求”代替逐条结果也无法通过。

### PQ26：为什么要设计 `start -> context -> submit -> next -> finish` 多个工具？

这是将定性操作和语义推理分开。`start` 固定审查输入并建立 case；`context` 按 Claim 分页提供证据；`submit` 接收当前阶段的结构化判断并校验；`next` 由运行时推进状态；`finish` 只在全部必要阶段完成后聚合报告。如果只暴露一个“review”工具，外部无法校验模型是否覆盖全部需求、是否完成反证和是否引用真实证据。

### PQ27：上下文过长或被截断怎么办？

当前工具不会一次性返回所有需求乘以所有代码。Claim 按游标分页，默认每页 3 条、最大 10 条；每条 Claim 最多返回有界的 Diff、源码 Symbol 和图边，单个源码片段还有字符上限。Agent 必须沿 `next_cursor` 读到结尾，覆盖率门禁再检查是否遗漏 Claim。如果图扩展达到预算，将产生 gap，在取证阶段对单个 Claim 定向扩展。

### PQ28：没有 base，只有当前仓库代码时能不能审？

可以做 snapshot 审查，即判断当前实现是否符合需求。但没有 base 时无法做变更级归因，不能可靠地说问题是本次 MR 引入、暴露，还是历史已存在。当前运行时将这类案例标记为 `snapshot`，归因应为 `unattributed`。如果要回答“本次 MR 是否导致了该问题”，就必须提供或从 MR 解析 base/head。

### PQ29：如何检验这个工具真的有效？

需要分三层验证：

1. 确定性运行时测试：验证索引复用、Diff 上下文、调用边唯一性、分页上界、L3 升级、伪 Claim 拒绝、证据归属、覆盖率和报告根因聚合。
2. 审查能力基准：对模型隐藏 oracle 和测试，只给需求与单个候选实现，检查完整版是否无误报，以及幂等、职责分离、重试策略和取消付款绕过等已知缺陷是否被发现。
3. 真实 MR 试点：由 reviewer 对结论做接受/驳回标注，统计根因召回率、精确率、`uncertain` 比例、证据完整度、审查耗时和人工复核时间。

只有模型在几个演示案例上说对了，不足以证明工具可用。

### PQ30：当前基准集具体验证了什么？

仓库中的费用支付基准集包含一个完整版和四类缺陷版：并发幂等不完整、缺失申请人与审批人职责分离、重试上限/退避/永久错误策略与需求冲突，以及后台付款路径绕过取消状态保护。基准使用独立合规测试和机器可读 oracle 验证每个版本的真实行为。当前 `run_benchmark.py` 主要验证候选版本是否符合 oracle 设定，不等于已经自动完成了对模型审查输出的全量评分。正式盲测时，oracle、合规测试和其他候选版本不能提供给被测模型，否则会造成答案泄漏。

### PQ31：如何证明四阶段比一次性审查更好？

不能只从流程看起来更严谨就下结论，需要做消融实验。在同一模型、同一需求与代码集上，分别运行单轮审查、去掉 challenge、去掉 investigate 和完整四阶段，比较根因召回、误报、不确定率、证据完整度和 token/耗时。如果 challenge 不能显著降低误报，或 investigate 无法降低不确定率，就应简化该阶段，而不是为了架构完整而保留。

### PQ32：如何验证索引和双向调用链确实有价值？

同样应该做召回层消融：比较“只给 Diff”“Diff + 文本搜索”“Diff + Symbol”和“Diff + Symbol + 双向调用图”四种证据策略。除最终缺陷命中外，还应统计真正支撑标准答案的源码是否出现在 Top-K 证据中。像“批处理入口绕过原子付款领取”这类跨路径案例，最能检验 callers/callees 扩展是否真正带来额外召回。

### PQ33：如果面试官问“当前方案最需要改进的技术点是什么”？

可以回答三点。第一，当前索引虽能复用未变文件，但仍会遍历并读取全部受支持源文件，需要基线索引、Git blob SHA 和真正的 MR 增量边更新。第二，当前调用解析主要是语法和名称级，可以在重点语言接入 LSP 或编译器语义，改善重载、多态和跨文件解析。第三，需要用真实 MR 标注集完成索引、四阶段和不同模型的消融实验，将工程上的“有机制”转化为数据上的“有效果”。

### PQ34：如果只用 30 秒说清整个技术链路，怎么回答？

> MR 进来后，系统先锁定 base/head，用 Git Diff 找到变更位置，再用 AST/Tree-sitter 将变更行映射到函数、方法和常量等符号。从这些变更符号出发，沿 callers 和 callees 补齐上下游代码，为每条需求生成有界、可引用的证据包。同一个专用 Agent 在状态机约束下完成初判、质疑、取证和收敛，后端再用 Claim 覆盖和 Evidence 归属校验防止跳步骤或无证据定案。

## 4. 答辩时必须主动说清的边界

1. 不说“替代人工审查”，说“辅助完成需求逐条对照和证据搜集”。
2. 不说“证据不足就是没实现”，说“证据不足标记 uncertain，交由人工复核”。
3. 不说“每次都全仓重建索引”，说“当前有哈希复用，生产方案是基线索引加 MR 增量”。
4. 不把 GitHub/PR 说成公司内部平台，统一表述为“内部 MR 平台适配层”。
5. 不把本地可运行说成全量生产上线；根据真实经历使用“完成工程实现”“完成试点接入”或“投入使用”。
6. 不虚构节省时间、命中率或用户量；如果没有测量，就说清验证方法和当前回归案例。
7. 不说“调用图能证明业务正确”，说“调用图用于证据导航，最终判断仍需要源码片段”。

## 5. 技术实现追问备查

### 5.1 背景与价值

#### Q1：为什么要做这个工具？

研发过程中，MR 代码审查通常关注代码质量、安全、性能和风格，但“代码是否完整实现需求文档”主要依赖人工经验。需求文档可能包含权限、状态流转、异常处理、幂等、审计等细粒度约束，人工逐条对照成本高，也容易漏。这个工具的目标是把需求声明和代码变更建立证据关联，辅助 reviewer 快速发现未实现、实现偏差或证据不足的点。

#### Q2：这个工具和普通 Code Review Agent 的区别是什么？

普通 Code Review Agent 更偏通用缺陷发现，例如潜在空指针、性能问题、安全风险。这个工具的审查目标更窄：判断代码实现是否满足需求文档。它不是泛化找 bug，而是围绕需求条目逐项建立证据链，再做一致性判定。

#### Q3：为什么这个问题适合用大模型？

因为需求文档和代码之间不是简单关键词匹配。需求可能写成“超过审批阈值需进入财务复核”，代码里可能体现为常量、状态枚举、审批方法和状态转移调用。大模型擅长做跨文本、跨代码语义理解，适合判断“需求语义”和“代码行为”是否一致。但大模型不能自由扫描和自由定案，所以需要确定性工具提供边界和证据。

#### Q4：这个项目的技术难点是什么？

核心难点是如何让大模型在有限上下文中做可靠审查。我的设计是把能力分成两层：底层运行时用确定性方法构建需求、Diff、符号和调用链证据；上层由大模型基于证据做语义推理，并通过状态机强制执行反证分析、补充取证和结论收敛。这样既利用模型理解能力，又控制幻觉和漏审。

#### Q5：项目最终产出是什么？

产出是一个可接入 Agent 平台的审查工具。它包含插件入口、专用审查 Agent、结构化工具接口和本地 Python 运行时。使用者可以通过命令传入需求文档和 MR 范围，工具自动完成审查并生成中文报告。

### 5.2 形态与架构

#### Q6：它到底是 Agent、插件、MCP，还是 Skill？

项目本体更准确地说是“代码-设计文档一致性审查 Agent 工具”。当前交付形态是 OpenCode 插件，里面注册了一个专用审查 Agent 和一组 `spec_review_*` 工具。MCP 是另一种可选接口形态，适合把这些工具暴露给更多 Agent 客户端。Skill 更像提示词和工作流说明，不足以概括这个项目，因为项目包含运行时、索引、状态机和证据管理。

#### Q7：为什么用插件形态？

插件解决的是“如何接入宿主 Agent 平台”。在当前实现里，`src/index.ts` 通过 OpenCode 插件机制注册 `/spec-review` 命令、`spec-review` Agent 和工具权限。这样用户不需要手动配置多套命令，也能把审查能力作为一个独立功能放进研发工作流。

#### Q8：为什么不是直接做成 MCP？

MCP 适合跨客户端复用工具能力，但它本身不负责定义完整审查流程和 Agent 行为。当前阶段目标是先在 OpenCode 中形成完整闭环，所以插件形态更直接。后续如果要让 Claude、Cursor、OpenCode 或公司自研 Agent 框架都调用同一套能力，可以把 `start/context/submit/next/finish` 等能力再封装成 MCP Server。

#### Q9：子 Agent 在这里的作用是什么？

子 Agent 是专用任务执行者。它只负责需求-代码一致性审查，不处理普通聊天、代码编辑或无关搜索。代码中的 prompt 明确限制它只能调用 `spec_review_*` 工具，不能使用 shell、grep、edit 等通用能力。这样可以把审查行为收敛到受控流程里。

#### Q10：主 Agent 和这个专用 Agent 有什么区别？

主 Agent 负责理解用户请求和分发任务；专用 Agent 负责执行固定审查流程。专用 Agent 的权限更窄、工具更固定、输出格式更受约束，因此更适合做可复现的工程审查，而不是开放式问答。

#### Q11：整体架构怎么描述？

可以描述为四层：入口层是 OpenCode 插件和命令；Agent 层负责语义审查和阶段提交；运行时层负责 Git、索引、状态机、证据和报告；存储层用 SQLite 记录 case、claim、evidence、stage_runs、symbols、edges 等结构化数据。

### 5.3 运行流程

#### Q12：一次审查从开始到结束怎么跑？

流程是 `start -> context -> submit -> next -> finish`。`start` 创建审查案例、解析范围、建立索引、解析需求声明；`context` 分页返回需求相关证据包；`submit` 提交当前阶段结构化审查结果；`next` 推进状态机；所有阶段完成后，`finish` 生成最终报告。

#### Q13：`spec_review_start` 做了什么？

`workflow.py` 中的 `start_case` 会校验输入范围，禁止在没有 MR、base、path 或 fullRepo 的情况下盲目全仓审查。之后它会解析 MR 或 base/head，调用 `build_or_update_index` 建立索引，生成 case_id，解析 Git Diff 形成 change_seeds，再调用 `load_claim_candidates` 从需求文档中提取 Claim。

#### Q14：为什么要强制审查范围？

没有明确范围时，模型容易把整仓上下文混在一起，既慢又不可靠。代码里如果没有 `pr/base/paths/fullRepo` 会直接报错。这是一个工程安全设计：审查必须知道“本次要审哪里”和“要对照哪些需求”。

#### Q15：`spec_review_context` 做了什么？

它会按 Claim 分页返回证据包。每个证据包包含需求声明、变更摘要、相关源码证据、调用图和证据缺口。代码中默认每页 3 条，最大 10 条；源码证据、Diff 证据、调用图节点都有上限，防止上下文爆炸。

#### Q16：`spec_review_submit` 为什么要求 JSON？

因为运行时需要校验阶段结果，包括 claim_id 是否真实、verdict 是否合法、evidence_id 是否属于当前 case 和当前 claim、是否覆盖全部目标 Claim。自然语言报告无法做这些校验，所以阶段输出必须结构化。

#### Q17：`spec_review_next` 为什么单独存在？

这是为了让状态推进受运行时控制。模型不能自己跳阶段。每个阶段必须先提交结果，运行时校验通过后才能进入下一阶段。这样可以避免 Agent 跳过质疑、取证或覆盖率检查。

#### Q18：`finish` 输出什么？

`report.py` 会汇总阶段结果，统计覆盖率，聚合同根因问题，生成面向用户的最终中文报告。报告重点应展示需求对应的缺陷、证据和结论，而不是把所有中间推理都暴露给用户。

### 5.4 需求解析与 Claim

#### Q19：需求文档怎么解析？

工具把 Markdown 文档按标题、段落和列表拆分为候选需求声明，并生成稳定的 `CLAIM-*` ID。每个 Claim 保留章节、原文、规范化 statement、可验证性和顺序号，后续审查必须逐条覆盖。

#### Q20：为什么要把需求拆成 Claim？

如果不拆分，模型容易把多个需求混成一个结论，导致漏审。拆成 Claim 后，可以做到逐条判定、逐条引用证据、逐条统计覆盖率。代码中的覆盖率门禁会拒绝 `UNKNOWN`、`REMAINING` 这类占位结果。

#### Q21：文档元信息怎么处理？

文档编号、版本、负责人、修订记录这类内容不是可执行代码行为，一般标记为 `not_applicable`。这能减少把文档元数据误判成代码未实现的情况。

### 5.5 Git Diff 与 MR 范围

#### Q22：Git Diff 在审查里起什么作用？

Git Diff 是审查入口。它定位本次 MR 改动的文件、行号和 diff 片段，并把这些变更映射到符号作为 change seeds。后续上下文扩展会优先从这些种子出发，而不是随机扫全仓。

#### Q23：没有 base 版本还能审吗？

可以，但只能做 snapshot 审查，也就是判断当前代码是否符合需求，不能可靠判断问题是不是本次 MR 引入。代码中 `scope.py` 会把无 base 的场景标记为 `review_type=snapshot`，归因通常只能是 `unattributed`。

#### Q24：为什么要锁定 base/head？

因为 MR 可能在审查过程中继续提交。如果不锁定 base/head，审查结论和代码版本可能不一致。当前实现会记录 base/head revision，发布前也设计了 head SHA 校验，避免把旧结论发布到新代码上。

#### Q25：如果公司内部不是 GitHub 怎么说？

可以说“当前开源适配代码里接口名是 `pr`，GitHub 模块是外部平台适配层；在公司内部落地时对应的是内部 MR 平台，核心机制仍然是解析 MR 元数据、锁定 base/head、拉取变更并生成 Diff。”

### 5.6 AST/Tree-sitter 索引

#### Q26：为什么要建符号索引？

需求和代码不是纯文本对应关系。符号索引能定位函数、方法、类、常量、变量和调用关系。例如金额阈值可能是常量，审批流程可能在方法里，状态变化可能通过 transition 调用体现。没有符号索引，只靠关键词很难稳定找到这些证据。

#### Q27：当前索引支持哪些语言？

代码中 `indexer.py` 定义了 Python、C/C++、Go、Rust、Java、JavaScript、TypeScript 等后缀。Tree-sitter 模块可用时使用 Tree-sitter 查询；如果不可用，Python 会降级使用标准库 AST；其他语言如果缺少语法模块，会登记文件但标记为 `backend_unavailable`，不会假装已经完成语义解析。

#### Q28：Python AST 具体提取什么？

当前 Python AST 会提取类、函数、方法、模块级常量、变量和调用边。比如 `visit_ClassDef`、`visit_FunctionDef`、`visit_Assign`、`visit_Call` 分别处理类、函数、赋值和调用。这使工具能识别阈值常量、状态枚举、业务方法和方法调用。

#### Q29：Tree-sitter 在这里怎么用？

Tree-sitter 用于跨语言语法解析。代码通过语言模块和 `queries/*-tags.scm` 提取 definition 和 reference，形成符号和调用边。它的价值是用统一机制支持多语言扩展。

#### Q30：解析失败怎么办？

解析失败不能当成“代码不存在”。当前实现会记录 parser backend 和 parse status，例如 `syntax_error`、`backend_unavailable`。审查时如果关键证据缺失，应该输出 `uncertain`，而不是定案为不一致。

### 5.7 调用链与证据构建

#### Q31：为什么要构建双向调用链？

只看修改函数内部容易漏掉上下游行为。向 callees 看可以知道当前逻辑依赖了哪些底层方法，向 callers 看可以知道哪些入口会触发它。很多一致性问题是“某个入口绕过统一校验”或“后台任务绕过原子状态流转”，这必须看调用关系。

#### Q32：调用图是如何扩展的？

`context.py` 中 `_bounded_graph` 会从种子符号出发，按 callers、callees 或 both 方向做有界 BFS。它会限制最大节点数和边数量，并记录 unresolved、ambiguous、budget_limit 等 gap，避免无限展开。

#### Q33：调用图本身能不能作为定案证据？

不能。调用图主要用于导航和发现上下文，不能单独证明运行时行为。代码 prompt 里也明确要求 consistent/inconsistent 必须引用上下文包中的 evidence_id，不能只靠调用图或符号名相似定案。

#### Q34：证据对象是什么？

证据对象是持久化的 diff 或 source 片段，带有 `EVID-*` ID、路径、行号、revision、内容和 metadata。模型最终结论必须引用这些 evidence_id。这样报告可以从结论回溯到具体文件和代码片段。

#### Q35：为什么要分页上下文？

需求文档和代码都可能很大，一次性塞给模型会超上下文，也会降低判断稳定性。当前实现按 Claim 分页，每页默认 3 条，每条只带 Top-K 相关证据。这样可以控制 token，也能保证逐条覆盖。

### 5.8 多阶段审查

#### Q36：L3 快速审查做什么？

L3 对所有 Claim 做一次快速判断，输出 `consistent`、`inconsistent`、`uncertain` 或 `not_applicable`。它强调覆盖率，必须覆盖全部真实 Claim。auto 模式下，只有 L3 中的 inconsistent 和 uncertain 会进入 L4 深审。

#### Q37：L4 为什么分四个阶段？

L4 模拟更严谨的人工审查过程：先初判，再质疑，再取证，最后收敛。初判提出候选问题；质疑主动找误报原因；取证围绕 gap 补充上下文；收敛再去误报、合并重复、定级和归因。这样能减少一次性判断带来的误报。

#### Q38：什么情况下从 L3 升级到 L4？

`workflow.py` 中 `_needs_deep_review` 会检查 L3 结果。如果存在 `inconsistent` 或 `uncertain`，或者模型显式设置 `escalate=true`，auto 模式会进入 L4。fast 模式不会升级，deep 模式会直接从 L4 开始。

#### Q39：为什么要有反向质疑？

因为模型初判容易把“未看到证据”当成“没有实现”。反向质疑阶段要求主动寻找替代路径、前置校验、配置开关、调用可达性、别名、生成代码等反证，只有反证无法推翻时才继续定案。

#### Q40：定向取证和普通搜索有什么不同？

普通搜索是开放式找信息；定向取证是围绕已有 gap 调用上下文工具，指定 claimId、query、direction 和 maxNodes。也就是说，取证必须服务于一个具体证据缺口，而不是让模型随意扩大范围。

#### Q41：收敛阶段做什么？

收敛阶段会剔除误报、合并同根因问题、确定严重级别和归因。比如多个需求条目都由同一个状态流转缺陷导致，仍然要逐 Claim 输出结论，但可以使用相同 root_cause_id，让最终报告按根因聚合展示。

### 5.9 质量控制

#### Q42：如何控制幻觉？

主要靠证据约束。模型只能引用运行时返回的 evidence_id；consistent 和 inconsistent 必须有证据；证据 ID 必须属于当前 case 和当前 claim；证据不足必须输出 uncertain。运行时会在 `submit_stage` 中做校验。

#### Q43：如何防止漏审？

靠 Claim 覆盖率门禁。每个阶段都有 expected Claim 集合，提交结果必须恰好覆盖这些 Claim。缺失、重复、额外 claim_id 都会被拒绝。测试中也覆盖了 fake ID 和 incomplete coverage 被拒绝的场景。

#### Q44：如何控制误报？

一是 evidence_id 约束，不能凭空定案；二是 L4 challenge 阶段强制反证；三是 investigate 阶段按 gap 补证；四是 converge 阶段要求不一致必须同时满足需求可验证、代码证据精确、替代路径已检查、与本次范围关系可辩护。

#### Q45：如何处理证据不足？

输出 `uncertain`。这是工具设计里很重要的一点：证据不足不是缺陷，也不是通过，而是需要人工确认或补充上下文的状态。

#### Q46：为什么报告要简化？

用户真正关心的是哪些需求没完成、证据在哪里、需要怎么处理。状态机阶段、完整 JSON、覆盖率细节更适合机器或审计使用，不适合放在用户主报告里。主报告应聚焦需求条目和不一致问题。

### 5.10 性能与大仓优化

#### Q47：大仓库每次都要全量建索引吗？

不应该。当前代码已经支持文件哈希复用：文件内容没变时复用前一次快照的符号和边，只解析变化文件。但它仍会遍历和读取所有源码文件计算哈希，并对当前快照的调用边做解析，所以在超大仓上还有优化空间。

#### Q48：更好的大仓设计是什么？

更合理的是“基线索引 + MR 增量覆盖 + 按需调用链扩展”。主干分支预先建立基线索引，MR 审查只解析新增或修改文件，以 Diff 命中的符号作为种子，在基线调用图上局部扩展。这样常规 MR 的成本主要和变更文件、受影响符号、局部调用链相关。

#### Q49：为什么不能只审 Diff？

只审 Diff 会漏掉未修改调用方、公共函数影响、状态流转入口、配置和权限路径。Diff 应该作为入口，而不是边界。正确做法是从 Diff 出发，按调用关系和需求相关性扩展到必要上下文。

#### Q50：索引还可以怎么优化？

可以把文件哈希升级为 Git blob SHA，避免每次读取全文件；把符号和边做内容寻址缓存，避免每个快照复制全部事实；边解析只针对变更符号和受影响边增量更新；后台维护主干基线索引，MR 审查时只做 delta overlay。

### 5.11 安全与边界

#### Q51：为什么默认只读？

需求一致性审查涉及业务语义，自动改代码风险高。当前设计默认只读，报告问题和建议；只有用户明确确认时才进入发布或建议修复流程。这样符合研发流程中的安全边界。

#### Q52：工具会不会修改业务代码？

默认不会。插件 prompt 明确禁止直接编辑业务工作区。即使后续生成 suggested_patch，也只是建议；需要人工确认后才能走 fix preview 或独立分支修复流程。

#### Q53：为什么要限制子 Agent 权限？

因为审查过程应该可复现、可控。如果允许它随意 shell、grep、edit，就绕过了证据系统和状态机，最终报告也无法保证可追溯。当前 prompt 限制它只能使用 `spec_review_*` 工具。

#### Q54：并发怎么处理？

运行时使用 SQLite 存储状态，并通过仓库级锁避免多个写者同时操作。设计目标是并发时给出有界等待或友好错误，而不是暴露原始 `database is locked`。

#### Q55：数据存在哪里？

审查案例、索引、证据和报告都存放在业务仓库的 `.spec-review/` 下。这样状态和仓库绑定，便于追踪和清理，也避免写到用户全局目录或 OpenCode 内部数据库。

### 5.12 发布与集成

#### Q56：结果如何回流研发流程？

当前设计包含发布预览和发布接口。安全做法是先生成 publish preview，让用户确认报告内容和 locked head SHA；真实发布前再次校验 head 没有变化，再把 Review Summary 或检查状态回流到代码平台。

#### Q57：为什么发布前要校验 head SHA？

因为 MR 可能在审查结束后又被推送新 commit。如果 head 变化，原报告对应的代码已经不是最新代码。校验 head SHA 可以避免旧审查结果污染新版本。

#### Q58：行内评论为什么复杂？

行内评论必须落在 Diff 的新行，也就是 RIGHT/new line。如果证据位置不是本次 Diff 中的可评论行，就不能随便发成行内评论，只能放到 summary。否则代码平台会拒绝评论或造成误导。

### 5.13 测试与验证

#### Q59：你怎么验证工具有效？

可以用带有已知缺陷的版本做回归验证。例如一个版本应当无缺陷，审查结果应该 consistent 或 not_applicable；另一个版本故意绕过原子 `claim_for_payment`，工具应该识别出已取消单据仍可能进入支付的问题。测试还应覆盖 fake claim_id、证据归属错误、覆盖率不完整、上下文分页和报告聚合。

#### Q60：怎么证明不是模型碰巧答对？

不能只看一次输出，而要看机制约束和回归用例。运行时强制结构化提交、证据引用、覆盖率门禁和阶段推进；测试中验证非法 ID、缺失覆盖、证据不归属会被拒绝。模型即使想凭空输出，也过不了运行时校验。

#### Q61：如果模型给出错误判断怎么办？

工具设计不是完全消除错误，而是把错误变得可发现、可复核。每个结论都有 Claim 和 Evidence，人工可以快速定位依据；证据不足会标 uncertain；L4 会主动反证和补证。后续可以通过用例集和 oracle 结果持续评估误报、漏报和不确定率。

### 5.14 取舍与不足

#### Q62：这个方案最大的不足是什么？

最大不足是静态分析无法完整覆盖动态行为，例如反射、依赖注入、运行时配置、跨服务调用和外部系统副作用。这些场景不能强行定案，需要标记为 uncertain 或接入更多运行时/平台证据。

#### Q63：Tree-sitter 调用图的准确性如何？

Tree-sitter 和 AST 能提供结构化语法证据，但调用解析仍有不确定性，尤其是动态语言、重载、别名和多态。当前代码会把调用边标记为 probable、ambiguous 或 unresolved，并把不确定边作为 gap，而不是把调用图当成绝对事实。

#### Q64：为什么不用完整编译器或 LSP？

编译器/LSP 的语义更准，但接入成本、环境依赖和跨语言复杂度更高。Tree-sitter/AST 更轻量，适合作为第一阶段的静态证据层。后续可以在关键语言或关键仓库上接入 LSP，提升调用解析和类型解析精度。

#### Q65：为什么不用向量数据库？

向量检索适合语义召回，但不能替代结构化证据。这个场景需要精确到文件、函数、行号和调用关系，所以 AST/Tree-sitter 是基础。向量库可以作为补充，用于需求和代码的语义召回，但最终定案仍要回到结构化 evidence。

#### Q66：为什么要用 SQLite？

SQLite 足够轻量，适合本地短生命周期运行时保存 case、stage、claim、evidence、symbols 和 edges。它不需要单独服务，部署简单，也适合“移动一个文件夹即可使用”的交付方式。

#### Q67：为什么不用全局数据库？

全局数据库会带来权限、清理、迁移和多仓隔离问题。把状态放在业务仓库 `.spec-review/` 下，边界更清晰，也更容易按仓库管理审查记录。

### 5.15 技术面试深挖回答

#### Q68：如果面试官问你负责了哪部分，怎么答？

可以回答：我负责了一致性审查工具的核心设计和工程实现，包括需求声明拆解、Git Diff 范围解析、AST/Tree-sitter 符号索引、双向调用链取证、多阶段审查状态机、证据引用校验、覆盖率门禁和报告生成。同时也设计了插件接入形态，使能力可以作为专用 Agent 接入研发工作流。

#### Q69：如果问你最核心的创新点是什么？

可以回答：核心不是单纯调用大模型，而是把审查问题拆成“证据构建”和“语义推理”两层。确定性运行时负责构建可追溯证据和约束流程，大模型只在证据范围内做需求-代码语义判断。这个设计比直接 prompt 更稳定，也比纯静态规则更能处理自然语言需求。

#### Q70：如果问你为什么这个项目不是 prompt 工程？

可以回答：因为 prompt 只是 Agent 层的一部分。项目还有运行时、索引、数据库、状态机、证据对象、Git Diff 解析、调用图扩展、覆盖率门禁和报告生成。模型输出如果不符合 Claim 覆盖、Evidence 归属和阶段要求，会被运行时拒绝。

#### Q71：如果问你如何降低误报和漏报？

可以回答：误报通过 evidence_id 约束、反向质疑、定向补证和收敛阶段控制；漏报通过 Claim 拆分、分页审查和覆盖率门禁控制。对于证据不足场景，不强行定案，而是输出 uncertain。

#### Q72：如果问你如何处理长需求文档？

可以回答：先拆成 Claim，再分页提供上下文。每页默认处理少量 Claim，每条 Claim 只带相关 Top-K 代码证据。运行时记录覆盖率，确保分页不会导致漏掉需求声明。

#### Q73：如果问你如何处理大仓库？

可以回答：当前实现支持未变化文件的哈希复用，但更工程化的方向是基线索引加 MR 增量覆盖。主干预先建索引，MR 只解析变更文件，并从 Diff 命中的符号做局部调用链扩展。这样审查成本从全仓规模相关，下降到与变更规模和影响范围相关。

#### Q74：如果问你如何处理跨文件调用？

可以回答：索引阶段提取调用边，取证阶段从 Diff 命中的符号向 callers 和 callees 双向扩展。这样既能看到当前函数依赖的下游实现，也能看到哪些入口会触发当前逻辑。

#### Q75：如果问你如何判断一个问题是本次 MR 引入的？

可以回答：必须有 base/head 对比。comparison 模式下可以基于 Diff、head 代码证据和必要的 base 信息做 introduced、exposed、pre_existing 判断；snapshot 模式只能判断当前实现是否符合需求，不能可靠归因。

#### Q76：如果问你为什么要把 uncertain 保留下来？

可以回答：因为证据不足时强行判定会增加误报或漏报。uncertain 是一种工程诚实的状态，表示工具已覆盖该需求，但当前证据不能支持定案，需要人工确认或补充上下文。

#### Q77：如果问你如何设计报告？

可以回答：报告应该面向研发人员，主视图只展示需求对应的问题、影响、证据和建议。consistent 可以汇总，不应占据主体；uncertain 单独列出证据缺口；中间阶段和机器可读结果保留给审计和调试。

#### Q78：如果问你如何接入公司内部 MR 平台？

可以回答：抽象一个 MR Provider 层，负责解析 MR URL、获取 base/head、拉取变更和发布评论。审查核心不依赖具体平台，只依赖 base/head、Diff 和发布接口。当前代码里的 GitHub 模块可以替换成内部平台适配器。

#### Q79：如果问你后续是否会做 MCP？

可以回答：会作为可选扩展。MCP 适合把 `start/context/submit/next/finish/publish-preview` 这些确定性工具暴露给不同 Agent 客户端。插件形态解决 OpenCode 内接入，MCP 形态解决跨客户端复用，两者不是冲突关系。

#### Q80：如果问你怎么评价这个项目的工程价值？

可以回答：它把原本依赖人工经验的需求实现审查流程，转成了可执行、可追踪、可复核的 Agent 工作流。即使不能完全替代人工，也能提前发现需求遗漏和实现偏差，减少 reviewer 在大文档、大 MR 中手动对照的成本。

## 6. 最推荐的答辩主线

如果时间只有 1 到 2 分钟，建议不从 Tree-sitter 或状态机起讲，而是按“问题—方案—难点—价值—边界”展开：

1. 问题：现有 MR 审查更容易发现代码本身的问题，但对“需求是否完整实现”缺少系统化逐条对照。
2. 方案：工具调取需求和 MR 变更，把需求条目与 Diff、相关符号和上下游调用证据建立关联。
3. 难点：不能只看 Diff，也不能把整个仓库丢给模型；需要从变更出发按需扩展证据，并严格区分“未实现”和“证据不足”。
4. 解决：用确定性运行时构建证据、约束阶段和校验覆盖，再由大模型完成跨需求与代码的语义判断。
5. 价值：把原本依赖 reviewer 经验的对照工作变成可执行、可覆盖、可回溯的辅助审查流程，并将问题提前到合入前。
6. 边界：它不替代人工、测试或静态扫描；当前默认只读，证据不足时输出 uncertain，生产推广还需要内部平台适配和真实仓库评估。

可直接口述：

> 这个项目解决的是 MR 审查中代码与需求难以系统对照的问题。我将需求拆成可验证声明，从 MR Diff 出发，结合符号索引和双向调用链构建必要的代码证据。最大难点是既不能只看 Diff 造成漏判，也不能无边界扫描整仓导致成本和干扰增加。因此我用确定性运行时负责证据召回、覆盖率和阶段约束，再引导大模型做初判、反向质疑、定向补证和结论收敛。工具的定位不是取代 reviewer，而是提前找出需求遗漏和实现偏差，并让每个结论都可以回溯到需求和代码证据。
